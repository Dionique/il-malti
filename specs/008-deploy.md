# 008 — Сборка и публикация

Прод — статический сайт на GitHub Pages плюс локальный сервер на Node для
разработки. Никакого бэкенда: всё, что нужно браузеру, лежит в `data/`.

## Сборка

### REQ-DEPLOY-01 — В публикацию попадают только рабочие файлы
`bin/build` собирает в `dist/` (или `--out <каталог>`) только то, что нужно
браузеру: `index.html`, `styles.css`, `app.js` и `data/*.js` из явного списка,
плюс самодостаточная `404.html`. Список явный: если файл данных добавили в
`index.html`, но забыли в сборку, сайт сломается — это ловится прогоном тестов
против собранного каталога.

**Проверка:** `bin/build`, затем `python3 tests/smoke.py --root dist`
(идентификатор REQ-DEPLOY-01).

### REQ-DEPLOY-02 — Исходники не отдаются наружу
Сервер (`server.js`) и хостинг не должны раскрывать `server.js`, `tools/`,
`tests/`, `bin/`, `deploy/`, `.git/`. Локальный сервер использует allowlist;
на GitHub Pages публикуется только содержимое `docs/`.

**Проверка:** `curl` по списку путей, идентификатор REQ-DEPLOY-02.

## Публикация

### REQ-DEPLOY-03 — Публикация завершается проверкой сборки
После `git push` нужно дождаться, пока Pages соберёт **именно этот коммит**:
сравнивается SHA из `pages/builds/latest` с локальным `HEAD`. Проверять только
статус `built` нельзя — он остаётся от предыдущей сборки, и тесты уйдут на
старую версию сайта.

**Проверка:** `bin/deploy`, идентификатор REQ-DEPLOY-03.

### REQ-DEPLOY-04 — Тесты прогоняются против живого сайта
Один и тот же набор проверок запускается в трёх окружениях: локально, против
собранного `dist/` и против опубликованного сайта. Это ловит и ошибки сборки,
и проблемы хостинга.

**Проверка:** `python3 tests/smoke.py --url https://dionique.github.io/il-malti/`,
идентификатор REQ-DEPLOY-04.

## Полный цикл

```bash
bin/deploy          # тесты -> сборка -> прогон против dist -> коммит -> push
                    # -> ожидание сборки Pages по SHA -> прогон против сайта
```
